# Docker Deployment

The production Compose stack runs one Node API process and one internal Nginx container. SQLite uses WAL mode and persists under `./data`. The container Nginx serves the Vite build and forwards `/api` to the API container with request and response buffering disabled.

## Prepare configuration

```bash
cp .env.example .env
openssl rand -base64 32
```

Set a stable `API_KEY_MASTER_KEY`, the final HTTPS `APP_ORIGIN`, and `COOKIE_SECURE=true`. Losing or changing the master key makes existing provider keys unreadable; users must enter them again.

## Start

```bash
mkdir -p data
sudo chown -R 1000:1000 data
chmod 700 data
docker compose up -d --build
```

The web container binds only to `127.0.0.1:3000`. Use the example at `deploy/nginx-site.conf.example` for the host reverse proxy and TLS termination. Do not publish the API container directly.

## Data and backups

The server stores only anonymous sessions, encrypted providers, model assignments, and call summaries in `data/ionailabs-canvas.sqlite`. It does not store canvas projects, generated images, imported media, audio, prompts, or full generation history.

Create an online SQLite backup with:

```bash
docker compose exec api npm run backup
```

Stop the stack before restoring a backup. Preserve both the database and the exact `API_KEY_MASTER_KEY`. Detailed commands and the outbound-traffic boundary are documented in `deploy/README.md`.

## Resource boundary

The stack is designed for a small single server, but model requests and streamed media still create public outbound traffic. Browser-local media storage reduces disk usage; it does not eliminate network egress.
