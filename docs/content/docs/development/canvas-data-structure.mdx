# Canvas Data Structure

## Storage

Canvas projects and My Assets use localForage with the `infinite-canvas` database and `app_state` store. Image blobs use `image_files`; audio blobs use `media_files`. Project JSON stores display URLs, `storageKey`, and metadata instead of large base64 payloads.

## Projects

```ts
type CanvasProject = {
  id: string;
  title: string;
  createdAt: string;
  updatedAt: string;
  nodes: CanvasNodeData[];
  connections: CanvasConnection[];
  backgroundMode: "lines" | "dots" | "blank";
  viewport: { x: number; y: number; k: number };
};
```

Projects persist nodes, connections, the background mode, and the viewport. Node positions and sizes use canvas-world coordinates; viewport `x` and `y` are screen translations and `k` is the scale.

## Nodes and connections

```ts
type CanvasNodeData = {
  id: string;
  type: "image" | "text" | "config" | "audio" | "group" | `${string}:${string}`;
  title: string;
  position: { x: number; y: number };
  width: number;
  height: number;
  metadata?: CanvasNodeMetadata;
};

type CanvasConnection = {
  id: string;
  fromNodeId: string;
  toNodeId: string;
};
```

Built-in nodes cover images, text, generation configuration, audio, and groups. Plugins use namespaced node type strings. Connections store only endpoint IDs and are removed with their connected nodes.

Common metadata includes content, prompt, status, generation mode, model, image size and quality, output count, image groups, `storageKey`, MIME type, and byte size. Generation mode is `text` or `image`; audio nodes only store local media metadata.

A multi-image generation remains one image node. It creates every result slot before requests begin, tracks each slot independently, and uses `primaryImageId` to select the main result. The first successful image becomes primary immediately.

## Media lifecycle

`uploadImage()` stores a Blob or data URL in `image_files`, creates an `image:<id>` storage key and a session-scoped object URL, and reads the image dimensions and file metadata. Audio files are stored in `media_files` and restored through their own storage keys.

Cleanup is reference-based. After nodes, canvases, or assets are deleted, the application collects every still-referenced storage key, removes unreferenced blobs, and revokes their object URLs. This prevents deleting a file that another canvas feature still uses.
